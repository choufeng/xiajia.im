# 滑坡谬误

> 「要是……那不就完蛋了？」——完蛋的前提，是中间那一连串「就」都成立。可你证明过吗？

---

## 一句话定义

**声称一个小的开端，会不可避免地引发一连串越来越糟的后果，最终走向灾难——却拿不出每一步「必然发生」的证据。**

滑坡本身不一定是错的：如果每一步真的有强证据支撑，从小开端确实能推到大后果。谬误出在**省掉了证据，把一连串「可能」当成「必然」**，靠「就会、就会、就会」的节奏吓人。

## 它长什么样

| 小开端 | 被断言的灾难终点 |
|--------|-----------------|
| 「允许远程办公」 | 「大家就会偷懒 → 公司就会垮」 |
| 「给孩子买手机」 | 「他就会沉迷 → 成绩就毁了 → 一辈子就完了」 |
| 「修个 bug 改这一行」 | 「就会越改越多 → 系统就乱了」 |
| 「这次破例一次」 | 「以后就管不住了 → 规矩就形同虚设」」

看那个模式：**每一步都只用「就会」连接，没有任何「为什么这一步必然发生」。** 好像一旦踩上斜坡，就只能一路滑到底，中间连个刹车都没有。

## 为什么这么好用

因为它**借了真因果的壳**。

「A 导致 B」是成立的逻辑，所以「A 导致 B 导致 C 导致 D」**听起来**也成立。问题是：每多一个「导致」，都要补一份证据。滑坡谬误偷偷把证据全省了，只留下吓人的终点。

而且它特别擅长**调动恐惧**。人脑对「灾难终点」反应强烈，对「中间有没有证据」反应迟钝。于是听众被终点吓住，忘了检查通往终点的路通不通。**恐惧是最不讲逻辑的推力。**

更微妙的一点：很多滑坡论证**赌的是情绪共鸣，不是事实**。讲的人未必信，但他知道「吓你一下」比「讲道理」更容易让你站队。

## 怎么识别与破解

核心一招：**要求对方把滑坡拆成台阶，逐级出示证据。**

### 听到时

别去反驳那个灾难终点（终点往往确实可怕，反驳会显得你在轻视风险）。直接问：

> 「从 A 到 B 这一步，证据是什么？从 B 到 C 呢？」

让每一级台阶各自证明。任何一级拿不出「为什么必然发生」，这条滑坡就断了。**只要有一级站不住，终点就不成立。**

### 说到时（自查是不是在滑坡）

把自己说的「一连串就会」拆开，给每一级补上「为什么」。补不出来，就是在滑坡。

> 三秒自检：我说的这一串「就会」，每一步都能换成「因为有 X 证据，所以」吗？换不动的，就是滑坡。

### 区分「真滑坡」与「谬误滑坡」

不是所有滑坡都是谬误。判断标准：

| | 真滑坡 | 滑坡谬误 |
|---|--------|---------|
| 各级之间 | 有机制、有证据 | 只有「就会」 |
| 中间 | 有刹车点（可拦截） | 假装刹不住 |
| 现实例子 | 历史上重复验证过 | 纯属推测 |

「少喝点酒也伤肝」是真滑坡（有医学证据链）；「今天喝一口明天就酗酒」是谬误滑坡（中间没证据）。

## 工程师视角

技术决策里滑坡谬误有两个高频变种：

**变种一：「保守主义滑坡」**——拒绝任何改动：

> 「改这个配置？万一出问题，线上就挂了，用户就流失，公司就完了。」

终点吓人，但中间的「万一」从没被量化过。破解：要他算「这一步出问题的概率」「这一步有什么回滚手段」。一量化，恐惧就掉了一半。

**变种二：「技术选型滑坡」**——为不存在的需求设计：

> 「现在不用这个分布式方案，将来用户量一上来就撑不住，撑不住就得重写，重写就晚了。」

「将来用户量上来」有多大概率？什么时候上来？这些都不问，直接跳到「必须现在就上复杂方案」。结果是**为一个可能永远不会到来的未来，提前背上现在的复杂度债。**

破解：**让每一级带上数字和时间点。** 「用户量到多少、什么时候、撑不住的指标是什么」。带不上的，就是空滑坡。

反向也要警惕——**「乐观滑坡」**：「这个功能加上去很简单，加完测试一下就上线了」中间的「简单」「一下」「就上线」全是滑坡，上线时往往才发现连锁问题。

## 一句话记住它

**听到一连串「就会」，就要求一连串「证据」。** 拆成台阶，逐级出示，站不住的一级就是断点。
